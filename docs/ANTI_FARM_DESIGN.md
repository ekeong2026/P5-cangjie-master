## 問題

現時模式一及模式三的同一題目可無限重複答對並持續加分（`js/app.js` → `saveStudentStats()`，第 396 行），學生只要反覆玩即可刷高排行榜分數。

模式一 31 字、模式三 37 字（已核對 `js/data.js`，兩者皆無重複字）。模式二現時**只記秒數、加總分為 0**（`js/app.js` 第 2731 行），所以玩模式二完全不影響總分榜，缺乏練習誘因。

## 目標

1. 排行榜分數反映「掌握不同漢字的進度」，而非重複次數。
2. 每字每天首次答對才增加正式分數；當天已得分字仍可練習但不加分。
3. 出題優先抽「今天尚未得分」的字；全部完成後進入不計分複習。
4. 首次答對判斷由後端執行，前端紀錄不可作為加分依據。
5. **模式二加入加分，但仍保留純秒數天梯**，兩者並存。

## 計分規則

### 模式一（連體字）／模式三（難字特訓）— 第一階段

- 每名學生、**每天**、每個字只有**首次答對**可增加正式總分及該模式分。
- 「每天」以**香港時間**日期為界，午夜 00:00 重置。
- 加分值沿用現行引擎算出的 `roundEarned`（含速度倍率、連擊、技能加成），**不改計分公式**。
- 該字當天已得分再答對：本輪 **+0**，顯示「這模式得分已到上限」。
- 一輪固定 5 關；一輪結束後集中提交一次結果。

### 模式二（分體字／手速賽）— 第二階段

**保留的部分（不變）：**
- 純秒數天梯：排行依 `effectiveFinalTime`（含準確度罰時），秒數越少越前。
- 週次隔離、生涯最佳、CPM、段位評定全部照舊。
- 本機最佳秒數紀錄（`p5_speed_*`）照舊。

**新增的部分：**
- 每個字在該「周次＋功課」組合中，**每天首次答對**加一次分。
- 加分值採現成公式：
  ```
  roundScore = Math.max(20, Math.round(150 - effectiveFinalTime * 2));
  20 字賽再 × 1.8
  ```
- 該字當天已得分再答對：**+0**，顯示「這模式得分已到上限」。
- 模式二分數**計入正式總分及 `mode2Score`**（現時永遠為 0）。
- 週次隔離：不同週次／功課的字庫各自獨立計分，同一字在不同週可各自得分。

**兩種排行榜並存：**

| 分頁 | 排名依據 | 模式二貢獻 |
|---|---|---|
| 🏆 討伐龍虎榜（總分榜） | 累計總分 | ✅ 新增貢獻 |
| ⚡ 手速天梯榜 | 完成秒數 | ✅ 原本就有 |

### 出題優先順序（模式一／三）

1. 抽取該學生**今天尚未得分**的字。
2. 不足 5 個時，以當天已得分的字補足（補足部分不計分）。
3. 當天全部字都已得分後，進入不計分隨機複習。

## 資料結構（後端）

### 雙層儲存：Sheet 為真相，Script Properties 為加速器

| 層 | 儲存位置 | 角色 | 讀寫時機 |
|---|---|---|---|
| **真相** | Sheet「掌握進度」工作表 | 永久記錄，可重建抽屜 | 每次交卷同步寫入 |
| **加速器** | `PropertiesService.getScriptProperties()` | 交卷時快速判斷 | 每次交卷讀寫 |

**為什麼要兩層**：Script Properties 讀寫比 Sheet 快約 10 倍（5–20ms vs 100–500ms），但**不能當唯一真相**——若意外清空即無法還原。Sheet 慢但可靠。兩者同步寫，兼具速度與安全。

### Sheet「掌握進度」工作表欄位

| 欄位 | 說明 |
|---|---|
| 班別 | P5A–P5F |
| 學號 | 1–36 |
| 模式一當日已得分 | 格式 `字:YYYY-MM-DD` 串接，例如 `更:2026-10-12中:2026-10-12` |
| 模式一最後更新日 | 最後寫入日期（香港時間） |
| 模式三當日已得分 | 同上 |
| 模式三最後更新日 | 同上 |
| 模式二當日已得分 | 格式含週次 `w7_hw1:字:YYYY-MM-DD` |
| 模式二最後更新日 | 同上 |
| 更新時間 | 最後更新時間戳 |

### Script Properties 鍵設計

| 鍵 | 內容 |
|---|---|
| `mb:{班別}_{學號}` | **壓縮格式（0F 定案）**：`v1|YYYY-MM-DD|模式一字|模式三字|週次:字,週次:字` |

格式示例：`v1|2026-10-12|中更|日|w7_hw1:中更,w8:日`

- 日期只存一次（全部資料同一天，因每日覆蓋）；模式一／三為單字直接串接；模式二按週分組、同組字共用週次前綴。
- 序列化／解析由 `MasteryCore.serializeDrawer`／`parseDrawer` 負責；無法辨識的內容一律回傳空抽屜，不拋錯。
- 鍵內字元不得含 `|` `,` `;` `:`（`validKey` 已拒絕），杜絕格式被撐破。

**關鍵規則：**

1. **每日覆蓋而非追加**：寫入時只保留「今天」的得分字。日期不等於今天即視為無效，直接覆蓋。
2. **單一 key 上限 9 KB**。
3. **總容量基準 500 KB**（保守值）：
   - 官方文件對總容量說法不一致（部分來源稱 500 KB，部分稱 9 MB），**一律按 500 KB 設計**。
   - **實測容量（0F 定案後）**：最壞情況（模式一 31 字全滿＋模式三 37 字全滿＋模式二同日四組各 42 字）
     - 壓縮格式：每生 **283 字元** → 210 生約 **60 KB** ✅
     - 若用未壓縮的「字:日期」逐一串接：每生 4,480 字元 → 210 生約 **921 KB** ❌ 超標
   - 結論：**壓縮格式不是優化，是含模式二時的必要條件**。
   - 「遊戲紀錄」與「成績總覽」不受此限；抽屜僅為加速器，遺失可由 Sheet 重建。
4. **容量監控**：交卷若遇容量錯誤，`MasteryStore.writeDrawer` 回報失敗（不拋錯），改為只寫 Sheet，不阻斷學生；`MasteryStore.usage()` 供教師選單檢查用量。
5. **抽屜可重建**：若抽屜遺失，可由 Sheet「掌握進度」表重建（教師選單提供此功能，屬後續工作）。

**設計取捨**：以「字＋日期」字串集中存於單一儲存格，而非逐字一行或逐日一行。理由：
- 不需每日新增資料列，資料量固定（每生一行）。
- 不需每日清理工作，跨日自動失效。
- 符合清單「集中保存在同一欄，不逐字新增進度行」的要求。

**私隱**：只用班別、學號，不存姓名。

## 更新與修復機制（第 4 版新增）

### 現況核對（已讀 `apps-script/Code.gs`）

`doPost` 每收一次成績執行 4 件事：

1. `appendRow` → 寫入「遊戲紀錄」。
2. `updateSummaryStudent_()` → **增量更新「成績總覽」單一學生的行**（含第 11 欄週次最佳秒數）。
3. 交卷**不再**清除排行榜快取（`DATA_CACHE_SECONDS = 60`，見 S4）。
4. 回傳成功。

因此「成績總覽」**本來就是交卷即更新**；教師選單的 `refreshSummary` 實為**重建／修復**工具（重掃全部紀錄、整張重算），不是日常更新工具。

另註（**已於任務 0C 改動**）：原設計中，學生端排行榜走 `doGet` → `readDataCached_()` → `readData_()` **掃描全表**得出，不讀「成績總覽」。
0C 後 `readData_()` **改為只讀「成績總覽」**，總覽由「只供教師檢視」升格為**排行榜的唯一來源**；原始紀錄只在重建或總覽為空時才被掃描。

### 總覽偏差標記（0C 新增）

排行榜改以總覽為來源後，總覽一旦落後於原始紀錄，排行榜就會顯示舊分數，且**不會自行恢復**。故：

- `updateSummaryStudent_()` 失敗時，`doPost` **仍回傳成功**（成績已在紀錄中），並設定 Script Properties `SUMMARY_DIRTY`。
- `writeSummary_()`（重建）成功後清除該標記。
- 教師選單（任務 0L）將顯示此標記，讓教師知道應執行重建。

> 這同時修掉了原有缺陷：舊版 `updateSummaryStudent_()` 失敗會回傳 error，前端以同一 `requestId` 重試卻被去重擋下而直接成功，**總覽永遠不會補寫**。

### 現行缺陷（修復機制的存在理由）

`doPost` 順序為「先寫紀錄、後更新總覽」：

```
appendRow(...)              ← 成功
updateSummaryStudent_(...)  ← 若拋錯
```

步驟 2 拋錯時，請求回傳 error，前端以**同一 `requestId`** 重試；但重試時 `hasRequestId_`（第 46 行）判定該筆已存在，直接回 `duplicate: true`，**不會補寫總覽**。

結果：**遊戲紀錄有該筆、成績總覽永久缺少該筆**，且該生之後每次交卷都從偏差值往上累加。→ 修復（重建）機制**不是選項，是必需**。

### 三層更新架構

| 層 | 時機 | 動作 | 目的 |
|---|---|---|---|
| **即時** | 每次交卷 | 寫「遊戲紀錄」＋累加「成績總覽」＋寫「掌握進度」 | 教師隨時看到最新 |
| **兜底** | **每天清晨 06:00**（定時觸發器） | 由「遊戲紀錄」重建「成績總覽」及「掌握進度」 | 修正任何偏差 |
| **備援** | 教師按選單 | 立即重建同一組表 | 需要時即時重算 |

**為何定時排在清晨 06:00**：`refreshSummary` 使用同一把指令碼鎖、持鎖數秒。白天執行會與學生交卷搶鎖，拉長學生等待。清晨時段完全錯開。

### 定時觸發器配額（已查證官方數據）

| 項目 | 數值 | 本設計用量 |
|---|---|---|
| Triggers 總執行時間 | **90 分鐘／天**（consumer）／6 小時／天（Workspace） | 約 **0.1 分鐘／天** |
| 每個指令碼觸發器數 | 上限 20 個 | 1 個 |
| 單次執行時間 | 上限 6 分鐘 | 重建約 2–5 秒 |

→ **配額不是瓶頸**。觸發時間約有 15 分鐘窗口、不精確，對重建無影響。觸發器失敗時 Google 會以電郵通知指令碼擁有者，屬可接受的告警方式。

### 硬性前置要求：鎖定時區

專案內**沒有 `appsscript.json`**，Apps Script 專案時區未寫入程式碼。本設計核心是「**每天**午夜重置」，若專案時區不是香港時間，「今天」的定義會出錯。

**必須建立 `apps-script/appsscript.json`**：

```json
{
  "timeZone": "Asia/Hong_Kong",
  "runtimeVersion": "V8",
  "exceptionLogging": "STACKDRIVER"
}
```

同時：定時觸發器的觸發時刻亦依專案時區，設定後須確認 06:00 為香港時間。

### 「遊戲紀錄」新增欄位

現行 `LOG_HEADERS` 共 11 欄（請求編號／接收時間／年級／班別／學號／模式／本次得分／本次擊倒數／完成秒數／題量／周次）。

新增第 12 欄 **「本次得分字」**，內容為該次提交中實際計分的字（模式一／三為漢字；模式二含週次前綴如 `w7_hw1:更`），以固定分隔符串接。

**理由**：使「掌握進度」可與「成績總覽」一樣，完全由原始紀錄推導重建。否則一旦「掌握進度」寫入失敗，只能整批重設。

### 「成績總覽」工作表欄位（0C 後為排行榜來源）

| # | 欄位 | 說明 |
|---|---|---|
| 1–3 | 年級／班別／學號 | 5／P5A–P5F／1–36，固定每生一行（216 行） |
| 4–8 | 累計得分／累計擊倒數／連體字得分／分體字得分／特殊字得分 | 逐筆累加 |
| 9 | 最佳10字秒數 | 跨週最快 10 字賽秒數；無紀錄為空 |
| 10 | 最後接收時間 | ISO 時間字串 |
| 11 | **週次最佳秒數** 🆕 | `w7:35.5;w9:40`；手速週榜（`speedByWeek`）的唯一來源 |

> 既有試算表只有 10 欄時，`ensureSheet_` 會自動補上第 11 欄標題；補欄後該欄為空，
> 手速週榜會暫時留白，直到執行一次重建（教師選單或每天 06:00）才會填滿。

### 重建涵蓋範圍

| 表 | 可否由原始紀錄重建 | 說明 |
|---|---|---|

### 教師端選單

`onOpen` 既有「更新成績總覽」，本批新增：

| 選單項 | 功能 |
|---|---|
| 更新成績總覽（既有，保留） | 由紀錄重建「成績總覽」 |
| 更新掌握進度 🆕 | 由紀錄重建「掌握進度」 |
| 重建進度抽屜 🆕 | 由「掌握進度」重建 Script Properties 抽屜 |

所有重建動作皆**由原始紀錄出發**，可重複執行且結果一致（冪等）。

## 同步問題與解法

### S1／S2：雙寫原子性（解法 3）

交卷時要寫抽屜（Script Properties）及 Sheet（真相）。為兼顧**速度**、**正確**及**可重建**，採用：

```
┌─ LockService 原子鎖（最小區段）─────────┐
│ 1. 讀抽屜進度（或由 Sheet 載入）         │
│ 2. 以伺服器時間判斷今天是否已得分         │
│ 3. 計算實際加分                          │
│ 4. 寫回抽屜                              │
└─────────────────────────────────────────┘
      ↓ 鎖已放開（持鎖約 50ms）
5. 盡力寫 Sheet「掌握進度」（失敗只記錄，不報錯、不阻斷學生）
```

- **計分權威是抽屜**（受原子鎖保護），不是 Sheet。
- **Sheet 為可重建的真相**：若抽屜與 Sheet 不一致，由教師選單的**補寫機制**比對並補齊差異。
- **S2 兩台裝置**：因「讀→判斷→寫」在同一把鎖內完成，後到的請求會看到已更新的抽屜，不會重複加分。

> 註：使用者原選「先抽屜後 Sheet（快）」，與 S2「原子鎖」需一致處理。本解法將抽屜置於鎖內、Sheet 置於鎖外，同時滿足速度與正確性。

### S3：離線補送

- 前端在遊戲完成時記錄**完成時間戳**，離線佇列連同時間戳保留。
- 補送時後端**驗證時間戳合理性**：不得超過現在 24 小時，也不得為未來時間。
- 補送分數**算在真正的完成當天**，不因補送延遲而歸入別天。
- 超出 24 小時的補送：記錄為「逾期」，由教師選單處理，不靜默丟棄。

### S4：排行榜快取

- 排行榜資料快取 **60 秒**。
- **交卷不強制清除快取**，接受最多 60 秒顯示延遲，避免多人同時開榜觸發重算。
- 快取與學年的關係：每個學年使用**另一份成績試算表**（新計分起點），亦即在 Apps Script 層是不同專案／不同快取命名空間，故快取 key **不需**再嵌入學年。原「key 含學年」一項在此前提下不適用，特此更正。

### S5：跨午夜

- 一律以**請求到達伺服器的時間**（香港時間）為準。
- 23:59 玩完但 00:01 到達 → 算隔天。
- 前端顯示的日期僅作提示，**不作計分依據**。

### S6：抽屜重建

- 抽屜若遺失或容量異常，由 Sheet「掌握進度」表重建。
- 重建功能置於教師選單，屬後續工作。
- 容量錯誤發生時：改為**只寫 Sheet**，不阻斷學生交卷。

## 後端介面

沿用現有 `apps-script/Code.gs`（帳號 A）的 `doPost`，擴充 payload：

```
{
  requestId,          // 固定，重試不得生成新 ID
  grade: 5, cls, num,
  mode,               // connected | special（第一階段）| speed（第二階段）
  round: [            // 逐字結果
    { char: '更', correct: true, earned: 18 },
    ...
  ],
  wordCount,
  weekKey             // 模式二必填
}
```

後端處理（在 LockService 鎖內）：

1. `requestId` 去重；重複請求直接回傳原結果，不重複計分。
2. 以香港時間取得今天日期。
3. 逐字比對：該字今日未得分且本輪答對 → 計入本次加分，寫入「字:今天」。
4. 該字今日已得分 → 忽略其 `earned`，加 0。
5. 只有寫入成功才回傳確認；前端收到確認才標示已同步。
6. 回傳新增得分字、本輪實際加分、該模式今日進度（例如 `3/31`）。

**向後相容**：未帶 `round` 的舊請求（前端舊版）按現行邏輯處理，不阻斷既有學生。舊格式紀錄照常累加。

**模式二路徑**：`mode === 'speed'` 由第二階段加入 `round` 及每日首答判斷；秒數欄位（`bestTime`）維持不變，天梯邏輯不動。

## 前端流程

### 第一階段（模式一／三）

1. 一輪 5 關進行中：本機記住每題結果（字、對錯、算出的 `roundEarned`），**不即時送後端**。
2. 一輪結束：組出 `round` 陣列，連同 `requestId` 送出一次。
3. 收到後端確認：套用實際加分（可能因該字今日已得分而被扣減）並更新進度顯示。
4. 送出失敗：保留待上傳資料，沿用現有可靠上傳機制，並存於本機待下次補送。
5. 進度顯示：「模式一：今日 3 / 31 字」、「模式三：今日 5 / 37 字」。
6. 該字今日已得分而答對時，該題顯示「這模式得分已到上限」，本輪 +0。

### 第二階段（模式二）

1. 手速賽進行中：照現行記錄秒數、準確度、失誤。
2. 賽事結束：照現行存本機最佳秒數、上傳秒數天梯資料。
3. **額外**：組出該場的字結果（哪些字答對）送出一次，取得每日首答加分。
4. 秒數天梯顯示不變；新增顯示本場獲得的分數。
5. 已得分字答對時同樣顯示「這模式得分已到上限」。

## 不在此批範圍

- 成績年度重設、PIN。
- 部署 Apps Script、發布網站、建立新 Repository。
- 現有累計分數的歷史處理：使用者將另複製一份 Google Sheet 作新計分起點，本機階段不連真表。

> 註：排行榜效能改善（P4）已納入本批，上列不再包含。

## 已確認規則（第 4 版）

1. 已得分字以「字＋日期」字串集中存單一儲存格。
2. **「首次」= 每天一次**，香港時間午夜重置；專案時區必須鎖定 `Asia/Hong_Kong`。
3. **模式二保留純秒數天梯，另加入每日首答加分。**
4. 加分值：模式一／三沿用 `roundEarned`；模式二沿用現成 `roundScore` 公式。
5. 出題優先抽「今天尚未得分」的字（模式一／三）。
6. **工作順序：先做模式一／三，再做模式二。**
7. **更新方式：交卷即時寫入為常態；另加每天 06:00 定時重建兜底；並保留教師手動選單。**
8. **「遊戲紀錄」新增「本次得分字」欄位**，使「掌握進度」可完整重建。

## 驗證方式

- **排行榜等價性（0C，已執行）**：以同一份虛構紀錄，比對「只讀總覽」與「掃描原始紀錄」兩條路徑的輸出，須逐欄完全相同；
  涵蓋重建後與交卷增量後兩種情境，並含重複 `requestId`、歷史無編號列、非 5 年級列、不存在的班別、20 字賽及不合法秒數。
  另斷言一般讀取期間不呼叫掃描函式（確實不再讀全表）。
- Node 內建測試：每日重置（同日重複加 0、跨日可再得）、requestId 去重、未得分字優先出題、舊格式請求相容、模式二秒數天梯不受影響、模式二週次隔離。
- 重建冪等性：以虛構紀錄重建「成績總覽」及「掌握進度」，重複執行結果一致；與增量更新結果相同。
- 時區：以固定時戳驗證香港時間日期換算，含 00:00 邊界及 UTC 前一日情況。
- Playwright：真實頁面虛構登入，一輪 5 題集中提交、同日重複顯示 +0 與上限提示、進度顯示正確、手速賽仍出秒數天梯並額外加分。
- 定時觸發器：本機階段**不建立實際觸發器**，只驗證重建函式可獨立執行且冪等。
- 虛構資料，不向正式接口寫入。
